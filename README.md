# 2027 ROBOCON 夏令营 —— 下位机代码

主控 STM32H723ZGTx（STM32H7 系列）+ STM32CubeMX + FreeRTOS，单主控板运行"归正翻转 KFS → 视觉识别 → 移动拾取/堆放 KFS → 上斜坡"全流程，四人协同开发。

## 目录结构

```
RobotLower computer/
├── APP/
│   ├── Core/          ← 机器人整体状态机（Robot_TypeDef / RobotInit / RobotStateUpdate），
│   │                     串联各模块，任务调度全部在这里（多人共用，改动需评审）
│   ├── Common/        ← 底层共享驱动与协议：电机驱动（GO_M8010、J60、M3508）、
│   │                     编码器、FDCAN 封装、气泵、Zigbee 与上位机通信、控制/策略算法
│   ├── Chassis/       ← 底盘（麦克纳姆轮）移动控制
│   ├── Flip/          ← KFS 翻转（归正）
│   ├── Pickup/        ← KFS 拾取状态机（含存底层/存上层/保持真空）
│   ├── Roboticarm/    ← 机械臂（升降 + 前伸 + 旋转关节电机）驱动与动作序列
│   └── Vision/        ← 与视觉上位机通信，判断 KFS 颜色是否需要抓取
├── Core/              ← CubeMX 生成，只做外设初始化和建任务，不写业务逻辑
├── Drivers/           ← HAL 库，不手动修改
└── Middlewares/       ← FreeRTOS
```

## 代码规范

### 模块职责

- **APP/Core**：全局唯一的强耦合点，包含：
  - 机器人整体状态机（任务调度：翻转 → 视觉判断 → 移动拾取/堆放 → 上斜坡 → 手动模式）
  - 模块间通信统一通过 `Robot_TypeDef` 中各子模块状态字段传递，各任务之间**不直接互相调用对方内部函数**
  - 改动 Core 前需要在群里同步，合并需至少 1 人 review
- **APP/Common**：驱动层/工具层，供其余模块调用的底层能力（电机、总线、通信协议、算法），非顶层业务逻辑，改动同样需要评审避免破坏多个模块
- **Chassis / Flip / Pickup / Roboticarm / Vision**：各自独立文件夹，只负责自己机构的实现，对外只暴露 `Init()`/动作函数供 Core 调用，内部实现互不干涉

### 编程范式

- 统一使用**状态机编程**：每个模块内部用 `枚举状态 + switch` 或函数指针表描述行为，不写裸的顺序逻辑/死等延时
- 状态命名统一前缀，例如 `FLIP_STATE_IDLE`、`FLIP_STATE_SEARCHING`、`FLIP_STATE_DONE`
- 模块之间的状态切换必须通过 Common 的事件/消息触发，禁止跨模块直接读写对方的静态变量

### 命名与宏定义规范

- 宏全部大写 + 模块前缀，例如 `#define CHASSIS_MAX_SPEED  2000`
- 函数名：模块前缀 + 大驼峰，例如 `Flip_Init()`、`Pickup_Task()`
- 每个模块暴露的公共接口写在对应 `.h` 文件里，内部私有函数/变量加 `static`，不导出
- 涉及具体引脚、外设、定时器编号的常量一律用宏定义，禁止在业务代码里写魔法数字

### `.ioc` 文件规则

- 谁需要新增外设/改动引脚，先在群里/Issue 里知会一声
- 只由一人负责在 CubeMX 里改动并 "Generate Code"，生成代码单独提交，commit 里不夹带业务逻辑改动
- 其他人改动前先 pull，避免 `main.c` / `stm32h7xx_it.c` 出现大范围冲突

## GitHub 使用规范

### 仓库结构：大仓库 + 小仓库

- **大仓库**（本仓库 `2027ROBOCONSummerCamp`）：下位机实际运行的整体代码，四人共同维护
- **小仓库**（个人仓库/Fork）：每人自己的开发仓库，用来调试自己负责的模块
  - 小仓库可以随意、高频 commit，方便本地开发时回退历史，不做规范约束
  - 自己模块在小仓库里跑通、自测没问题后，再把代码同步/提交到大仓库

### 大仓库分支策略

- `main`：**只允许出现稳定版本**，任何时候都必须是可直接烧录、跑得通完整流程的状态
- `dev`：集成测试分支，个人模块开发完成后先合并到这里，与其他模块联调测试
- 合并顺序：**小仓库个人代码 → 大仓库 `dev`（联调测试）→ 测试通过后 → 大仓库 `main`**
- 禁止把未经测试的代码直接合并到 `main`

### 提交与合并

- 提交到大仓库 `dev` 建议通过 PR，写清楚改动的模块和内容
- `dev` → `main` 的合并必须经过团队确认（至少联调跑通一次完整流程），合并后可打 tag 标记版本（如 `v0.1-task1-demo`）
- commit message 建议带模块前缀，例如 `feat(flip): 完成翻转动作状态机`、`fix(chassis): 修复定位漂移`
